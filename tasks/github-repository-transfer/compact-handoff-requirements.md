# Compact ownership-transfer handoff requirements

This operation generates a handoff. Generation must make zero GitHub transfer
requests. Running the handoff later is a separately authorized operation.

The qualified context remains Linux x86-64 with Cat Food's Grease command at
`/opt/catfood/bin/grease`, the pinned Grease/Oils runtime closure, GNU coreutils,
curl and authenticated GitHub CLI. Android packages exist in Cat Food's inventory,
but their distinct runtime versions and paths are not this qualification.

The maintained producer must retain the complete standalone artifact and may
also render a shorter, inspectable paste unit. That unit must visibly invoke
`transfer-github-repository.grease` with explicit source owner, repository,
destination owner, expected login, numeric repository ID and execution context.
It must acquire only an immutable Kitchen source and check its exact SHA-256
before execution. It must not require a checkout, working directory, previous
variable, numbered helper or generic shell. A link alone is not a handoff.

The downloaded program must perform the same login, numeric identity, canonical
source, administrator capability, destination identity/type/membership, collision,
visibility, durable pending-attempt and independently observed postcondition
checks as the complete artifact. A pending attempt must not be resent merely
because the terminal's working directory changed. Acquisition failure, partial
download, changed bytes and missing tools must make zero transfer requests.

The normal state belongs to the authenticated user's home directory, under
`.local/state/kitchen/github-transfers`. Changing homes is changing durable input
state; qualification does not claim to reconstruct a lost pending ledger. Each
positive or negative fixture uses a fresh home. Reruns use that same home and a
different fresh terminal/directory. Already-moved identity must require no POST.

The paste unit must keep the parent terminal alive after child failure and print
an explicit unverified outcome. Wrapper completion is not operation success.
Only the inner verified markers plus independent API observations establish a
verified transfer. Tests must check the exact generated paste bytes, repeatable
generation, both personal and organization positives, all existing thirteen API
scenarios, acquisition tampering/partial failure, pending reruns, absent checkout,
spaces and quotes, and parent state/survival. An always-refuse program must fail
the positive controls. No test makes a live transfer.

Acceptance binds the exact parameters, standalone and paste bytes, maintained
generator, recipe bytes, source acquisition pin/digest, checker and runtime
closure. Recipe, checker, runtime, parameters, acquisition policy or delivered
byte changes invalidate that evidence. Repeating unchanged generation does not
require a new full-system audit, but mutable login/repository/destination state
must still be observed before any separately authorized live mutation.
